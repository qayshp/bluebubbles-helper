# Find My SearchParty Beacon Set Record - 2026-07-06

## Purpose

Document the structure of one `SPBeacon` record returned by `SPOwnerSession allBeaconsWithCompletion:` while anonymizing personal identifiers. This is the concrete set/array data shape observed after converting the completion result from `NSSet` to `NSArray`.

## Source

The data came from the debug-only beacon probe:

```text
debug-findmy-searchparty-beacons-start
debug-findmy-searchparty-beacons
```

The helper called:

```objc
SPOwnerSession allBeaconsWithCompletion:
```

The completion returned:

```text
result_class: __NSSetI
element class: SPBeacon
```

The helper converted the set to an array before serialization:

```objc
NSArray *beacons = @[];
if ([beaconsResult isKindOfClass:[NSArray class]]) {
    beacons = beaconsResult;
} else if ([beaconsResult isKindOfClass:[NSSet class]]) {
    beacons = [(NSSet *)beaconsResult allObjects];
}
```

## Probe Metadata Shape

```json
{
  "status": "completed",
  "probe_id": "AAAAAAAA-BBBB-CCCC-DDDD-EEEEEEEEEEEE",
  "session_id": "0x600000000000",
  "result_class": "__NSSetI",
  "beacon_count": 53,
  "serialized_count": 53,
  "started_at": 1783380269.520556,
  "completed_at": 1783380273.281625
}
```

Notes:

- `probe_id` is a UUID string generated by the helper.
- `session_id` is the runtime object pointer string for the captured `SPOwnerSession`.
- `started_at` and `completed_at` are Unix timestamps with fractional seconds.
- `result_class` was `__NSSetI`, so callers must not assume an array.

Field observations:

- `batteryLevel` is serialized as a string in the raw direct-field summary.
- `identifier` is present as an object, but the compact summary currently preserves only its Objective-C class.
- `role` is present as an `SPBeaconRole` object.
- `serialNumber` is the item serial-like string.
- `stableIdentifier` keeps the format `a:/<UUID>~#<SERIAL>`.

Field observations:

- `id` and `identifier` are UUID strings derived from the beacon identifier.
- `name` is the user-visible Find My item name.
- `deviceClass`, `deviceModel`, and `rawDeviceModel` are currently normalized to `beacon`.
- `modelDisplayName` is currently normalized to `Find My Item`.
- `batteryStatus` is currently `Unknown` even when raw `batteryLevel` is present.
- `prsId` is currently `owner`.
- `locationEnabled` and `locationCapable` are hard-coded true for this debug serialization shape.
- `findmy_beacon.description` and `findmy_beacon.role` are runtime descriptions and should not be treated as stable identifiers.

## Why Location Is Not Present

The `SPBeacon` set appears to be an identity and inventory list, not a location result list. The record includes stable identity, role, serial, model classification, and coarse battery fields, but it does not include latitude, longitude, horizontal accuracy, address, timestamp, or a location object.

Observed SearchParty evidence supports that split:

- The passive `SPOwnerSession allBeacons` getter was nil.
- The async `allBeaconsWithCompletion:` call returned a populated `NSSet` of `SPBeacon` objects.
- Passive session caches such as `locationCache`, `locationSources`, and `clientObservedBeacons` were empty during the observed run.
- `setLocationUpdateBlock:` receives an `SPLocationFetchResult`.
- `SPLocationFetchResult locationsByBeaconIdentifier` was observed, but returned empty dictionaries in the observed run.

Current interpretation: `SPBeacon` identifies what items and devices exist. Location likely arrives through a separate SearchParty location fetch/update path keyed by beacon identifier or stable identifier. The next target is to populate or trigger `SPLocationFetchResult locationsByBeaconIdentifier`, then join those location records back to the `SPBeacon` inventory using the beacon UUID or stable identifier.
